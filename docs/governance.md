# 관리체계: 게이트 · 기록 · 수명

**이 리포는 1인 개발이다.** 그래서 코드를 봐 줄 다른 사람이 없다. 그 몫을 사람이 아니라
**게이트와 규칙**이 대신한다. 이 문서는 그것이 무엇이고 어디에 적혀 있는지를 한자리에 모은다.
여기서 새로 정하는 것은 없고, 흩어져 있는 것을 가리킬 뿐이다.

> **§ 표기**: 별도 언급이 없으면 [규정서](regulation.md)의 절 번호다.

## 숫자

| | 지금 | 세는 법 |
|---|---|---|
| 커밋 | 253 (2026-08-05 이후, 2026-08-26 기준) | `git log --oneline \| wc -l` |
| 릴리스 | 16 | `gh release list` |
| 자동 게이트 | 11 | `Makefile`의 `all` 타깃 |
| 테스트 함수 | 227 | `grep -rh '^func Test' --include='*_test.go' . \| wc -l` |
| 케이스 그룹 | 4 (`TD`·`TV`·`TP`·`TK`) | [테스트 맵](test-map.md) |
| 설계 문서 | 규정서 · 아키텍처 · 단계별 셋 · 수용 원칙 · 호환성 · 검토 중 | [docs/](README.md) |

**리포에서 센 값이라 세는 법을 함께 적는다.** 어긋나면 이 표가 틀린 것이다. [테스트 맵](test-map.md)도 같은 규칙을 쓴다.

**그 말이 참인지 게이트가 대신 센다.** `check-docs`가 커밋·자동 게이트·테스트 함수 셋을 직접 세어
이 표와 대조하고, 어긋나면 막는다. 커밋 수만은 폭을 두어 20개까지 뒤처지는 것을 넘어가 주는데,
커밋마다 정확히 맞기를 요구하면 게이트가 매 커밋 깨지기 때문이다. **릴리스 수는 세지 않는다.**
`gh`와 네트워크·인증에 기대는 값이라 게이트에 넣으면 그것이 없는 자리에서 검사하지 못한 것을
통과로 읽게 된다(§2.6). 그 한 줄은 릴리스할 때 손으로 맞춘다.

## 무엇이 자동으로 막히나

`make` 하나가 열한 가지를 돌리고 **CI가 그 전부를 다시 돌린다**([`.github/workflows/ci.yml`](../.github/workflows/ci.yml)).
게이트를 건너뛰고 올리는 길이 없다.

| 게이트 | 막는 것 |
|---|---|
| `generate` | 생성 코드가 proto와 어긋난 채 올라가는 것. 재생성 후 차이가 있으면 실패한다 |
| `lint` | 계약(proto) 스타일 위반 |
| `breaking` | **이미 나간 계약을 깨는 변경.** 마지막 릴리스 태그와 대조한다 |
| `fmt-check` | 포맷이 어긋난 채 올라가는 것 |
| `vet` | Go 정적 검사가 잡는 것 |
| `check-boundary` | 이 리포가 자기 밖을 설명하는 문장 |
| `check-docs` | 끊어진 링크·앵커, 낡은 범위 표현, 역할분담 산문, 개인정보. **그리고 문서가 실물과 어긋나는 것** 넷: 라이선스 표와 실제 의존(아래 「라이선스 표가 낡지 않게 막는다」), 위 「숫자」 표·[테스트 맵](test-map.md)의 레벨 분포와 실제로 센 값, **한국어 문서와 영문 짝의 뼈대**, 문서가 적은 **Go 버전과 `go.mod`** |
| `check-collectors` | 릴리스가 **빌드하는** collector와 플레이북이 **반입하는** collector가 갈리는 것 |
| `build` | 호스트뿐 아니라 **linux/amd64·windows/amd64 교차**가 깨지는 것 |
| `build-jar` | JVM 사이드카 빌드 |
| `test` | 단위·통합 테스트 전부 |

**게이트는 실제로 겪은 문제에서 나왔다.** `check-collectors`는 v0.6.6에서 Windows 번들에
`pqcota-jvmscan`이 빠져 릴리스만 받아 돌리면 실패하던 문제를 겪은 뒤에 만들었다. `check-docs`가 Go로 쓰인 것도 셸 `grep`이
Mac과 리눅스에서 한글 문장을 다르게 세어 같은 게이트가 서로 다르게 판정했기 때문이다.

## 무엇을 검증하나

케이스는 명세에 적히고, **그 번호가 곧 테스트 파일 링크**다. 그래서 테스트가 없는 항목은 감출 곳이 없다.

**레벨별로 몇 개가 어디서 도는지는 [테스트 맵](test-map.md)이 혼자 들고 있다.** 한때 같은 표가
여기에도 있었는데, 같은 숫자를 두 곳에 적으면 한쪽만 고쳐진다. 그 표도 「리포에서 센 값」이라고
밝히므로 `check-docs`가 unit과 integration을 직접 세어 대조한다.

**툴체인 버전도 게이트가 잰다.** Go 버전이 문서 아홉 곳에 적혀 있어 툴체인을 올리면 손으로 다
맞춰야 했다. SSOT인 `go.mod`의 `go` 지시자와 대조한다. 릴리스 노트만은 보지 않는데, 지난 릴리스가
어떤 툴체인으로 나갔는지는 그때의 사실이라 지금 값과 달라도 맞기 때문이다.

**한국어 문서와 영문 짝도 게이트가 잰다.** 문장은 언어마다 다르지만 뼈대는 같아야 하는데, 한쪽에만
절이나 항목을 더하면 링크 검사로는 잡히지 않는다. 그래서 `##` 절의 수와, 절마다 `###` 소제목 수·최상위
목록 항목 수를 대조한다. 제목의 글자는 비교하지 않는다. 번역이라 다른 것이 맞다. 실제로 이 게이트를
만들자마자 일곱 곳이 갈려 있었다. 로드맵 항목 셋이 영문에만 없었고, v0.6.4는 한국어만 줄이고 영문은
긴 채였으며, 절 셋이 통째로 번역되지 않은 채였다.

**스킵은 통과가 아니다.** `PQCOTA_TEST_DSN`이 없으면 Postgres 케이스를, JDK가 없으면 attach
케이스를 건너뛴다. 그 사실을 통과로 세지 않는다. 어느 케이스를 건너뛰면 무엇을 확인하지 못한
것인지는 [테스트 맵](test-map.md)에 적혀 있다.

**실물로 확인한 것과 아닌 것을 가른다.** 커널 하한 3.2는 KVM VM에서, Windows CNG는 실제 장비에서
확인했다. [데모가 덮지 못하는 것](../demo/integration-verification.md)도 따로 적어 둔다.

## 무엇을 기록하나

[릴리스 노트](../RELEASE_NOTES.md)가 스스로 규칙을 정해 두었다.

- **절을 내용의 종류로 나눈다.** 만든 것 · 알아낸 것 · 고친 것
- **결함을 기능으로 포장하지 않는다.** 자기 절에 적고 세 가지를 밝힌다. 무엇이 잘못이었나, 어느
  버전부터인가, 무엇이 잘못 나왔나
- **발행된 절은 사실을 바꾸지 않는다.** 문장과 분량은 다듬을 수 있지만, 읽는 사람이 아는 사실이
  달라지면 안 된다

그래서 릴리스 노트에 실패가 남는다. 번들이 깨져 있었다는 것도, 화면과 문서가 다른 이름을 쓰고
있었다는 것도 그 버전의 「고친 것」에 있다.

## 결정이 어떻게 사는가

설계에는 수명이 있다([검토 중인 설계](under-review.md)의 머리말).

```
① 로드맵 등재    방향이 생기면 릴리스 노트의 로드맵에 한 줄
② 여기서 설계    코드는 아직 바꾸지 않는다. 무엇이 걸리고 무엇을 정해야 하는지까지
③ 본 설계로 승격  구현이 확정되면 단계별 설계 문서로 옮기고 검토 중에서는 지운다
④ 안 하기로      로드맵의 「안 만드는 것」으로 옮긴다
```

**본 설계 문서는 지금 결정된 것만 적는다.** 검토 중인 것이 섞이면 무엇이 사실이고 무엇이 계획인지
읽는 사람이 가릴 수 없기 때문이다. 지금 ②에 살아 있는 것은 서버 역할 엣지 관측, 엣지 상대의 스코프
판정, 통신 관측의 주기 분리 셋이다.

**「안 만드는 것」도 적는다.** 플릿 오케스트레이션, 원격 실행 엔진, 소스 스캐너, 동적 추적, 판정과
점수화가 그것이다. 방향이 아니라 경계라 언젠가 오리라 기대하지 않도록 적어 둔다.

## 무엇에 기대나: 오픈소스 선택

[라이선스 정리](licensing.md)가 **라이선스 축**을 본다면 여기는 **선택 축**이다. 어느 부문에 무엇을
도입했고 왜 그것인지, 그리고 **만들지 않기로 한 것**과 그 근거다. 이 리포의 성격상 뒤쪽이 더 중요하다.
관측 도구는 범위를 넓히자면 끝이 없어서, 무엇을 만들지 않을지를 정하지 않으면 경계가 없어진다.

### 부문별로 무엇을 도입했나

| 부문 | 무엇 | 왜 그것인가 |
|---|---|---|
| **계약·직렬화** | Protobuf · gRPC | 계약이 단일 진실이라 스키마를 코드보다 먼저 고정해야 한다. 하위호환을 **도구가 검사**해 주는 것(`buf breaking`)이 결정적이었다 |
| **표준 산출물** | CycloneDX CBOM (ECMA-424) | 크립토 자산 목록의 표준이 이미 있다. 자체 포맷을 만들면 다른 도구와 못 섞인다 |
| **저장** | PostgreSQL (`pgx`) | append-only 이력과 JSONB가 함께 필요했다. 여러 노드를 시간에 걸쳐 쌓을 때만 쓰고, 한 번 훑는 경로는 저장소 없이 돈다 |
| **OS 프리미티브** | `golang.org/x/sys` | AF_PACKET 원시 소켓. 표준 라이브러리가 덮지 않는 유일한 부분이다 |
| **오케스트레이션** | Ansible | 노드 도달은 이미 풀린 문제다. 자체 원격 실행 엔진을 만들지 않는다(§4.4) |
| **코드 생성** | `buf` · `protoc-gen-go` · `protoc-gen-go-grpc` | 생성 결과가 사람마다 달라지지 않게 **버전을 고정**한다 |
| **CI** | GitHub Actions · dependabot | 게이트 열한 가지를 건너뛸 수 없게 만드는 곳이다 |
| **그림** | Graphviz | 토폴로지를 DOT로 내고 렌더는 밖에 맡긴다. 산출물(SVG)은 데이터다 |
| **관측 대상 런타임** | OpenSSL · JDK/JCA · Windows CNG · BouncyCastle · oqsprovider | 만드는 것이 아니라 **보는 대상**이다. 각각의 열거 API를 그대로 쓴다 |
| **표준·규격** | NIST FIPS 203/204/205 · RFC 4253 · IANA TLS 코드포인트 | 이름과 판정 기준을 스스로 정하지 않는다 |

### 직접 의존이 다섯뿐이다

```
github.com/jackc/pgx/v5      google.golang.org/grpc      google.golang.org/protobuf
golang.org/x/sys             gopkg.in/yaml.v3
```

관측 대상이 **레거시 서버**라서 그렇다. 소스도 패키지 관리도 기대할 수 없는 구형 호스트에 복사해서
실행하고 지우면 끝이어야 하므로, `CGO_ENABLED=0` 정적 단일 바이너리가 전제가 된다. 의존이 늘면
그 전제가 흔들린다.

그래서 표준 라이브러리로 되는 일은 표준 라이브러리로 한다. ELF 파싱은 `debug/elf`, TLS·SSH 핸드셰이크
파싱은 직접 구현했다. 실제로 10년 된 배포판(CentOS 7·Debian 8)과 musl(Alpine)에서 같은 바이너리
하나가 돈다.

### 만들지 않기로 한 것

이쪽이 이 리포의 실제 설계다. 각 줄에 근거가 붙어 있다.

| 만들지 않은 것 | 대신 | 근거 |
|---|---|---|
| **원격 실행 엔진** | Ansible 등 사용자의 substrate | 노드 도달은 이미 풀린 문제다. 부가가치는 그 위의 게이트·서명·완전성 맵에 있다(§4.4) |
| **소스·아티팩트 CBOM 스캐너** | CBOMkit 등이 낸 표준 CycloneDX를 **받는다** | 소스가 있으면 CI가 이미 보고 있다. 겹쳐 만들 이유가 없고, 파일만 오가므로 라이선스도 전염되지 않는다 |
| **패킷 캡처 라이브러리**(libpcap) | 순수 Go AF_PACKET | 정적 링크를 지키려면 C 의존을 들일 수 없다. 필요한 것은 핸드셰이크 프레임뿐이라 직접 읽는 편이 작다 |
| **외부 조회 도구**(`ldd`·`lsof`·`ss`·`readelf`) | `/proc`·ELF 직접 파싱 | 레거시 서버는 최소 이미지이거나 도구가 없거나 버전이 제각각이다. 외부 도구에 기대면 **관측 실패가 환경 탓으로 흩어져** 무엇을 못 봤는지조차 모른다 |
| **JDK 동봉**(jlink 미니 런타임) | Go로 attach를 직접 구현 | attach는 Java 기능이 아니라 OS IPC다. 머신에 JDK가 있으면 그것을 재사용하고, 없어도 붙는다. 번들 크기가 런타임 유무와 무관해진다 |
| **Kotlin·Gradle** | `javac` 하나로 빌드 | 사이드카는 클래스 몇 개다. 빌드 도구를 들이면 기여자의 전제가 늘어난다 |
| **cosign·sigstore** | ed25519 detached 서명 | 투명성 로그와 레지스트리 접근을 전제해 **에어갭과 상충**한다. 이미 있는 서명 인프라와 결이 같고 오프라인에서 완결된다 |
| **동적 추적**(eBPF·ltrace) | 회선에서 실제 협상을 관측 | 침습적이다. 관측 대상이 프로덕션 레거시라 대가가 크다 |
| **판정 엔진·점수화** | 관측 사실만 낸다 | 도구가 대신 판단하면 「🔴는 판정이 아니라 관측」이라는 선이 무너진다 |

### 도입한 것을 어떻게 경계 짓나

**GPL 도구는 프로세스 너머에 둔다.** intake 계약이 그것을 강제한다. GPL collector는 gRPC나 CLI 뒤에
서고, 주고받는 것은 CycloneDX와 Envelope뿐이라 코어 내부 타입이 넘어가지 않는다. 자세한 것은
[라이선스 정리 §5](licensing.md).

**provider 파일은 도구가 주지 않는다.** 어느 provider를 쓸지 고르고 그 파일을 구해 오는 일은 계획을
쓰는 쪽이 한다. 도구가 보장하는 것은 **그 파일이 그대로 배치됐다**(sha256)까지다. 검증서는 빌드 단위라
파일만 봐서는 FIPS 검증본인지 알 수 없다. 그래서 확인도 사용자가 한다.

**표준의 이름을 바꾸지 않는다.** TLS 그룹 코드포인트는 IANA 등록값을 그대로 쓰고, 모르는 값은
`unknown(0xNNNN)`으로 적는다. SSH 협상은 RFC 4253의 규칙대로 계산하고 한쪽만 관측했으면 지어내지
않는다. 성숙도 이름은 NIST 표준 문서 번호에 건다.

### 라이선스 표가 낡지 않게 막는다

`checkdocs`가 `go list -deps`로 **실제 링크되는 모듈을 버전까지** [라이선스 정리](licensing.md)의 표와
대조한다. 표에 없으면 「링크되는데 공개되지 않았다」로, 버전이 다르면 「어느 버전을 검토했나가 거짓이
된다」로 실패한다.

**의존 갱신을 일부러 자동화하지 않았다.** dependabot은 GitHub Actions만 켜 두었다. `go.mod`을 봇이
올리면 그 표가 낡는데 봇은 표를 고치지 못해 PR이 게이트에서 멈춘다. 직접 의존이 다섯뿐이라 취약점
알림을 받고 손으로 올리는 편이 싸다고 판단했다. 그 이유는 [`dependabot.yml`](../.github/dependabot.yml)에
적어 두었다. 라이선스 표를 **생성**하도록 바꾸면 그때 켤 수 있다.

### 접은 선택지

한 번 검토하고 접은 것들이다. 다시 꺼낼 근거가 생기면 그때 본다.

- **jlink 미니 런타임 아카이브**: 필요 없다고 결론지었다. 머신의 JDK를 재사용하고, 없으면 Go 네이티브 attach가
  덮는다. attach 가능 JDK가 전무한 환경이 실제로 확인되면 재검토한다.
- **eBPF dynamic-trace**: 침습적이라 하지 않기로 했다. 어휘(`dynamic-trace`)는 계약에 남아 있는데,
  어휘는 계약이고 구현 여부와 별개다.
- **UI**: 리뷰 큐와 확정 버튼이 따라오고, 그 둘은 이 리포가 명시적으로 뺀 것이다. 화면 위에서는
  「여기서 승인도 하자」가 자연스러운 다음 걸음이 되어 관측 도구가 판정 도구가 된다.

## 계약을 지키는 법

계약(`contracts/*.proto`)이 단일 진실이고, 그것을 깨지 않는 규칙이 [호환성 정책](compatibility.md)에
다섯 면으로 갈라 적혀 있다. 계약에는 순수 additive만 넣는다. 서명은 범위를 바꾸면 과거가
무효가 된다. Go API는 지우지도 바꾸지도 않고 더하기만 한다. DB 스키마는 멱등하게 이행한다.
옛 바이너리를 조용히 받아 주지 않는다.

이 가운데 첫째는 게이트가 강제한다. `make breaking`이 마지막 릴리스 태그와 대조해 CI에서 돈다.

## 1인 개발이라는 사실

**GitHub의 Issues와 Pull requests는 거의 비어 있다.** 이슈 한 건, PR 두 건인데 둘 다 dependabot이
올린 의존성 갱신이다. 혼자 만들면서 자기에게 PR을 보내지 않았다. 그 사실을 감출 이유가 없다.

**대신 리뷰가 하던 일을 셋이 나눠 맡는다.**

- **게이트**가 기계로 잡을 수 있는 것을 맡는다. 계약을 깨는 변경, 생성 코드 드리프트, 끊어진 링크,
  두 곳으로 갈라진 목록이 그렇다
- **설계의 수명**이 결정을 남긴다. 무엇을 왜 안 하기로 했는지가 「안 만드는 것」에, 아직 정하지 못한
  것이 「검토 중인 설계」에 남아 다음에 같은 판단을 다시 하지 않는다
- **릴리스 노트의 기록 규칙**이 실패를 남긴다. 결함을 기능으로 포장하지 않으므로 무엇이 언제부터
  틀렸는지가 이력에 그대로 있다

**바깥에서 온 검토도 있었다.** 계약을 소비하는 쪽에서 온 지적이 v0.5.0의 여섯 항목을 짚었고, 그
사실이 그 릴리스의 절에 적혀 있다. dependabot이 올린 두 PR도 실제로 병합해 운영한 이력이다.

**그래도 비어 있는 것은 비어 있다고 적는다.** 사람 리뷰어가 없다는 것은 이 리포의 한계이고, 그것을
게이트로 완전히 대신할 수 있다고 말하지 않는다. 관측하지 못한 것을 없다고 적지 않는 원칙(§2.6)을
리포 자신에게도 적용한다.
