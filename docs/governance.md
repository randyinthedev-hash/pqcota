# 관리체계: 게이트 · 기록 · 수명

**이 리포는 1인 개발이다.** 그래서 코드를 봐 줄 다른 사람이 없다. 그 자리를 사람이 아니라
**게이트와 규칙**이 대신한다. 이 문서는 그것이 무엇이고 어디에 적혀 있는지를 한자리에 모은다.
여기서 새로 정하는 것은 없고, 흩어져 있는 것을 가리킬 뿐이다.

> **§ 표기**: 별도 언급이 없으면 [규정서](regulation.md)의 절 번호다.

같은 규칙을 쓴다.

## 무엇이 자동으로 막히나

`make` 하나가 열 가지를 돌리고 **CI가 그 전부를 다시 돌린다**([`.github/workflows/ci.yml`](../.github/workflows/ci.yml)).
게이트를 건너뛰고 올리는 길이 없다.

| 게이트 | 막는 것 |
|---|---|
| `generate` | 생성 코드가 proto와 어긋난 채 올라가는 것. 재생성 후 차이가 있으면 실패한다 |
| `lint` | 계약(proto) 스타일 위반 |
| `breaking` | **이미 나간 계약을 깨는 변경.** 마지막 릴리스 태그와 대조한다 |
| `fmt-check` · `vet` | 포맷과 정적 검사 |
| `check-boundary` | 이 리포가 자기 밖을 설명하는 문장 |
| `check-docs` | 끊어진 링크·앵커, 낡은 범위 표현, 역할분담 산문, 개인정보 |
| `check-collectors` | 릴리스가 **빌드하는** collector와 플레이북이 **반입하는** collector가 갈리는 것 |
| `build` | 호스트뿐 아니라 **linux/amd64·windows/amd64 교차**가 깨지는 것 |
| `build-jar` | JVM 사이드카 빌드 |
| `test` | 225개 |

**게이트는 겪은 것에서 나왔다.** `check-collectors`는 v0.6.6에서 Windows 번들에 `pqcota-jvmscan`이
빠져 릴리스만 받아 돌리면 실패하던 일을 겪고 만들었다. `check-docs`가 Go로 쓰인 것도 셸 `grep`이
Mac과 리눅스에서 한글 문장을 다르게 세어 같은 게이트가 서로 다르게 판정했기 때문이다.

## 무엇을 검증하나

케이스는 **명세에 적히고 번호가 곧 테스트 파일 링크**다. 그래서 테스트가 없는 항목은 감출 곳이 없다.

| 레벨 | 수 | 어디서 도나 |
|---|---|---|
| unit | 214 | 어디서나. 입력은 테스트 내부 상수 |
| integration | 11 | 리눅스 필요. 실 crypto/tls · 실물 sshd · `CAP_NET_RAW` · 실 JVM · Postgres |
| e2e | 1 | [데모](../demo/README.md) 6단계. 생성물을 실제 노드에 적용하고 되돌리는 데까지 간다 |

**스킵은 통과가 아니다.** `PQCOTA_TEST_DSN`이 없으면 Postgres 케이스가, JDK가 없으면 attach 케이스가
건너뛰어지는데 그 사실을 통과로 세지 않는다. 무엇이 스킵되면 무엇을 확인하지 못한 것인지는
[테스트 맵](test-map.md)에 적혀 있다.

**실물로 확인한 것과 아닌 것을 가른다.** 커널 하한 3.2는 KVM VM에서, Windows CNG는 실제 장비에서
확인했다. [데모가 덮지 못하는 것](../demo/integration-verification.md)도 따로 적어 둔다.

## 무엇을 기록하나

[릴리스 노트](../RELEASE_NOTES.md)가 스스로 규칙을 정해 두었다.

- **절을 내용의 종류로 나눈다.** 만든 것 · 알아낸 것 · 고친 것
- **결함을 기능으로 포장하지 않는다.** 자기 절에 적고 세 가지를 밝힌다. 무엇이 잘못이었나, 어느
  버전부터인가, 무엇이 잘못 나왔나
- **발행된 절은 사실을 바꾸지 않는다.** 문장과 분량은 다듬을 수 있지만, 읽는 사람이 아는 사실이
  달라지면 안 된다

그래서 릴리스 노트에 실패가 남는다. 번들이 깨져 있었다는 것도, 화면과 문서가 다른 이름을 쓰고
있었다는 것도 그 버전의 「고친 것」에 있다.

## 결정이 어떻게 사는가

설계에는 수명이 있다([검토 중인 설계](under-review.md)의 머리말).

```
① 로드맵 등재    방향이 생기면 릴리스 노트의 로드맵에 한 줄
② 여기서 설계    코드는 아직 바꾸지 않는다. 무엇이 걸리고 무엇을 정해야 하는지까지
③ 본 설계로 승격  구현이 확정되면 단계별 설계 문서로 옮기고 검토 중에서는 지운다
④ 안 하기로      로드맵의 「안 만드는 것」으로 옮긴다
```

**본 설계 문서는 지금 결정된 것만 적는다.** 검토 중인 것이 섞이면 무엇이 사실이고 무엇이 계획인지
읽는 사람이 가릴 수 없기 때문이다. 지금 ②에 살아 있는 것은 서버 역할 엣지 관측, 엣지 상대의 스코프
판정, 통신 관측의 주기 분리 셋이다.

**「안 만드는 것」도 적는다.** 플릿 오케스트레이션, 원격 실행 엔진, 소스 스캐너, 동적 추적, 판정과
점수화가 그것이다. 방향이 아니라 경계라 언젠가 오리라 기대하지 않도록 적어 둔다.

## 오픈소스를 어떻게 고르나

직접 의존이 다섯뿐이고, 무엇을 만들지 않기로 했는지가 근거와 함께 적혀 있다
([오픈소스 활용](oss-adoption.md)). 라이선스 축은 [라이선스 정리](licensing.md)가 보고, **표가 실제
의존과 맞는지는 게이트가 검사한다.** `checkdocs`가 `go list -deps`로 실제 링크되는 모듈을 버전까지
대조해, 표에 없으면 「링크되는데 공개되지 않았다」로 실패한다.

## 계약을 지키는 법

계약(`contracts/*.proto`)이 단일 진실이고, 그것을 깨지 않는 규칙이 [호환성 정책](compatibility.md)에
다섯 면으로 갈라 적혀 있다. 계약은 순수 additive만, 서명은 범위를 바꾸면 과거가 무효가 되므로 신중히,
Go API는 지우지 않고 바꾸지 않고 더한다, DB 스키마는 멱등하게, 옛 바이너리를 조용히 받아 주지 않는다.

앞의 하나는 게이트가 강제한다. `make breaking`이 마지막 릴리스 태그와 대조해 CI에서 돈다.

## 1인 개발이라는 사실

**GitHub의 Issues와 Pull requests는 거의 비어 있다.** 이슈 한 건, PR 두 건인데 둘 다 dependabot이
올린 의존성 갱신이다. 혼자 만들면서 자기에게 PR을 보내지 않았기 때문이고, 그 사실을 감출 이유가 없다.

**대신 리뷰가 하던 일을 셋이 나눠 맡는다.**

- **게이트**가 기계적으로 잡히는 것을 잡는다. 계약을 깨는 변경, 생성 코드 드리프트, 끊어진 링크,
  두 곳으로 갈라진 목록이 그렇다
- **설계의 수명**이 결정을 남긴다. 무엇을 왜 안 하기로 했는지가 「안 만드는 것」에, 아직 정하지 못한
  것이 「검토 중인 설계」에 남아 다음에 같은 판단을 다시 하지 않는다
- **릴리스 노트의 기록 규칙**이 실패를 남긴다. 결함을 기능으로 포장하지 않으므로 무엇이 언제부터
  틀렸는지가 이력에 그대로 있다

**바깥에서 온 검토도 있었다.** 계약을 소비하는 쪽에서 온 지적이 v0.5.0의 여섯 항목을 짚었고, 그
사실이 그 릴리스의 절에 적혀 있다. dependabot이 올린 두 PR도 실제로 병합해 운영한 이력이다.

**그래도 비어 있는 것은 비어 있다고 적는다.** 사람 리뷰어가 없다는 것은 이 리포의 한계이고, 그것을
게이트로 완전히 대신할 수 있다고 말하지 않는다. 관측하지 못한 것을 없다고 적지 않는 원칙(§2.6)을
리포 자신에게도 적용한다.
