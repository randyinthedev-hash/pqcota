# 런타임 확장 계약 — 계약이 어디까지 버티나 (설계 노트)

> **성격**: 코드 무변경 설계 노트. enum도, substrate도, render도 건드리지 않는다.
> **목적**: §0.5가 주장하는 *"코어 무변경, 3축만 정의하면 새 암호 런타임을 수용한다"* 를,
> 가장 이질적인 후보 셋(정적 Go · 비-POSIX Windows CNG · backend성 HSM)을 **반례로 놓고**
> 종이 위에서 검증한다 — 부하 시험이 아니라 **설계 가정을 반례로 때려보는 것**이다. 산출물: (1) 어떤 코어 가정이 실제로 하중을 받는가, (2) HSM은 새 런타임인가
> 아니면 backend인가, (3) 기여자가 "새 런타임을 확장하려면 어디를 건드리나"를 한눈에 볼 온보딩 기준.

§0.5(암호 런타임 추상 원칙)는 런타임별로 달라지는 것이 **(a) 수집 방법, (b) 버전·provider 축
스키마, (c) remediation taxonomy** 세 가지뿐이라고 말한다. 이 노트는 그 주장을 있는 그대로
받지 않고, **실제로 버티는 층과 부러지는 층을 코드에 대조해** 가른다.

---

## 1. 확장 계약 — 현행 코드가 새 런타임에 요구하는 것

§0.5의 세 축을 실제 코드 지점에 매핑하면 이렇다. **넷째 축이 §0.5에 명시돼 있지 않다** — 이 노트의
핵심 발견이다.

| 축 | 무엇 | 코드 지점 |
|---|---|---|
| (a) **수집** | collector가 `CollectionResult`(CycloneDX + Envelope)를 emit. `detection_method` 필수 | `discovery/collectors/<runtime>/` |
| (b) **스키마 축** | `CryptoRuntime` enum 값 + `Finding.runtime_axes` oneof에 `XxxAxes` 추가 | `contracts/.../common/v1/common.proto`, `.../discovery/v1/cbom.proto` |
| (c) **remediation taxonomy** | 공통 `RemediationKind`(런타임 무관) + `Render`의 런타임 분기(`renderXxx`) | `plan.proto`(Kind enum), `pkg/provisioning/render.go`→`openssl.go`·`jca.go` |
| (d) ★ **substrate** *(암묵)* | 아티팩트를 **POSIX 파일**로 경로에 스테이징 + config 조각 + **파일 제거로 롤백** | `pkg/provisioning/paths.go`(`ModulePath(provider, jca bool)` → `/opt/pqcota/*.so\|*.jar`), `stage.go`(Ansible `copy`), `rollback.go`(`state: absent`), `record.go`(append-only) |

### 계약이 조용히 요구하는 하중 가정 셋

1. **provider 동형성**(§1.1) — "provider로 알고리즘 능력을 주입한다"가 성립해야 `PROVIDER_INJECT`·
   `CONFIG_ONLY`가 의미를 갖는다. 이게 없으면 remediation은 `REBUILD` 한 방향으로 붕괴한다.
2. **POSIX 파일 substrate**(위 (d)) — 아티팩트가 파일이고, 경로에 스테이징되고, 제거로 가역.
   openssl·jca가 **둘 다 POSIX 파일**이라 이 가정이 지금껏 `jca bool` 2-way 스위치 뒤에 숨어 있었다.
3. **관측 distinct** — 기존 collector가 이미 보는 것과 **다른 것**을 봐야 한다. 안 그러면 새 런타임이
   아니라 기존 런타임의 중복이다.

## 2. 반례 셋 — 가장 이질적인 후보로 때려보기

각 후보를 네 축으로 통과시키고, **어느 하중 가정에 걸리는지**를 본다.

### 2.1 정적 Go (`crypto/*`)

| 축 | 통과 여부 |
|---|---|
| (a) 수집 | 정적 ELF 심볼 / `debug/buildinfo` → `artifact`/`symbol-analysis` 레인(**inferred-low**, `confirmed` 아님). 런타임 introspection 대상(provider)이 **없다**. 협상 알고리즘은 netcap이 언어무관으로 와이어에서 이미 관측 |
| (b) 스키마 | `GoAxes`? 담을 게 buildinfo·module 정도로 **얇다** |
| (c) taxonomy | provider 모델 부재 → **`REBUILD` 하나뿐**. 이미 비-config 주석으로 일반 처리됨 → 새 `renderGo` **불필요** |
| (d) substrate | 배포할 파일 아티팩트가 **없다**(재빌드는 CI 몫). 스테이징 대상 0 |

**판정: 계약은 버티지만, 버팀의 방식이 "흡수"다.** 하중 가정 1(provider 동형성)이 성립하지 않아
`REBUILD`로 붕괴한다. 새 enum·render·substrate가 **전부 불필요**하고, Go는 이미 `REBUILD` taxonomy +
symbol 레인으로 **표현 가능**하다. → §0.5의 "코어 무변경" 주장은 성립하나, Go는 *새 런타임*이 아니라
*기존 taxonomy의 소비자*다.

### 2.2 비-POSIX Windows CNG

| 축 | 통과 여부 |
|---|---|
| (a) 수집 | **새 OS**. `BCryptEnumProviders`·레지스트리 introspection. 기존 `/proc`·ELF·AF_PACKET collector 재사용 **0** |
| (b) 스키마 | `CngAxes`(KSP/SSP 목록)는 oneof에 **깔끔히 추가 가능** — 확장점이라 코어 무변경 |
| (c) taxonomy | **두 겹으로 갈린다.** Kind 어휘(`PROVIDER_INJECT`=KSP 등록, `CONFIG_ONLY`=SCHANNEL/GPO 암호군)는 런타임 무관이라 **분류는 재사용 O**. 그러나 `Render`가 내는 **실제 아티팩트**는 openssl의 `[openssl_init]` 텍스트가 아니라 레지스트리/GPO/PowerShell — 그 아티팩트가 곧 (d)라 **render 층은 (d)와 분리 불가** |
| (d) substrate | ★ **여기서 부러진다.** DLL + 레지스트리 키 / GPO / `Register-CngProvider`. `ModulePath(/opt/pqcota/*.so)`·Ansible `copy`·파일 제거 롤백이 **전부 안 맞음**. `jca bool` 2-way로 표현 불가 |

**판정: CNG는 절반만 얹힌다.** (a) 콜렉터는 구현이 100% 신규이나 intake 계약은 재사용, (b) 스키마는
순수 additive로 **지금 당장 가능**, (c)는 **Kind 분류까지만** 맞고 구체 아티팩트 렌더는 (d)로 넘어간다.

- **디스커버리·인벤토리 절반**: ✅ 지금 프레임에 얹힌다 — enum + `CngAxes` + Windows 콜렉터면 자산이
  인벤토리에 정직히 뜬다(정규화·귀속·이력 그대로).
- **프로비저닝 절반**: ❌ substrate에 막힌다 — 적용 가능한 remediation 아티팩트를 현재 substrate로
  못 낸다.

그래서 "코어 무변경" 주장이 **substrate 층에서만 거짓**이 되고, Windows는 "3축 추가"가 아니라
**"(d) substrate 일반화 + 새 배포 백엔드"** 를 요구하는 별도(대형) 트랙이다. 그 일반화는 **이 구현이
손에 있을 때** 해야 한다 — Windows 구체 사례 없이 Registry/GPO 인터페이스를 미리 뽑으면 잘못된 seam을
뚫는다(투기적 추상화 금지).

### 2.3 backend성 HSM / PKCS#11

| 축 | 통과 여부 |
|---|---|
| (a) 수집 | **distinct.** 로드된 PKCS#11 모듈·슬롯 관측(libssl soname과 다른 것). `Pkcs11Axes` 값 있음 |
| (b) 스키마 | 축은 distinct — oneof 확장 가능 |
| (c)(d) taxonomy·substrate | ★ **핵심** — remediation이 대개 **openssl(`pkcs11-provider`)** 또는 **jca(`SunPKCS11`)** 를 HSM으로 *가리키는* 것이다. 즉 렌더는 기존 `renderOpenSSL`/`renderJCA`의 `PROVIDER_INJECT`에 "이 provider의 target이 HSM 슬롯"이라는 파라미터를 얹는 것. substrate(파일 스테이징 + config 조각)는 **재사용** |

**판정: HSM은 새 `CryptoRuntime` enum(peer)이 아니라 — (1) 새 디스커버리 axis + (2) openssl/jca
provider가 가리키는 backend target 으로 모델링하는 게 옳다.** §1.1 "provider 동형" 프레임에서 HSM은
*provider가 아니라 provider가 가리키는 하드웨어 백엔드*다. 진짜 peer인 경우는 앱이 벤더 `.so`를
openssl/jca **없이 직접 링크**할 때뿐이고, 그마저 provider 동형 대상이라 openssl-계열 render로 근사된다.

> **정직성 각주(§2.6)** — HSM 하드웨어가 PQC를 아직 지원 안 하는 건은 억지 아티팩트를 지어내지 않고
> `DECOMMISSION`·`APP_RECONFIG` 주석으로 정직히 처리된다. taxonomy가 이미 이 비-config 종류를 갖고 있다.

## 3. 결론 — 계약은 어디까지 버티나

| 후보 | 새 enum? | 새 render? | substrate 영향 | 판정 |
|---|---|---|---|---|
| 정적 Go | ✗ | ✗ | 없음(배포물 0) | `REBUILD` taxonomy로 **흡수** |
| Windows CNG | ✓ | ✓ | ★ **부러짐**(새 백엔드 필요) | 별도(대형) 트랙 — substrate 일반화는 구현과 함께 |
| HSM/PKCS#11 | **✗(권장)** | 기존 provider에 target 파라미터 | 재사용 | 새 **axis + backend target**, enum 아님 |

**버티는 층**: (a) 수집, (b) 스키마 oneof, (c) taxonomy 어휘 — 셋 다 확장점으로 설계돼 있어 새
런타임/축을 **코어 변경 없이** 받는다(검증됨).

**안 버티는 유일한 층**: (d) substrate의 **"POSIX 파일" 가정**. non-POSIX(Windows)에서만 부러진다.
HSM·Go는 이 가정을 건드리지 않는다(HSM=파일 재사용, Go=배포물 없음).

**그래서 §0.5의 "3축"은 정확히는 3.5축이다** — (a)(b)(c) + (d) substrate. (d)는 openssl·jca가 둘 다
POSIX 파일이라 지금까지 드러나지 않았던 **암묵 축**이다. 이 노트가 그걸 명시화한다. (§0.5 본문에 이
넷째 축을 한 줄 추가하되, **추상화 구현은 Windows 착수 시** — 지금은 문서로만 못박는다.)

### HSM 정체성 — 확정

HSM/PKCS#11 = **새 enum 아님.** 디스커버리 axis 신설 + openssl/jca provider의 **target(backend)** 으로
매핑. 직접 링크 앱만 좁은 peer 후보이고, 그마저 openssl-계열 render로 근사.

### §0.5 후속 목록의 재조정

§0.5는 `.NET CNG · Python cryptography · Go crypto · Node`를 후속 확장 대상으로 나열한다. 반례
테스트는 그 목록이 **"provider 동형" 가정에서 균일하지 않다**는 걸 드러낸다:

- **Python `cryptography`** — 링크한 libcrypto라 openssl 수집·remediation으로 **붕괴**. enum 아님. →
  기존 openssl 경로에 **`app_keys`(Python 앱 귀속)·usage_context**로 흡수.
- **Node.js** — 대체로 OpenSSL 배달 차량. 고유점은 **정적 임베드**(그건 artifact 레인) + `--openssl-config`
  노브. 새 provider 모델 아님 → openssl-계열로 흡수.
- **.NET** — 하부 OS에 따라 **CNG(Windows) 또는 OpenSSL(Linux)** 로 내려가는 언어 표면. 자기 substrate가
  없다 → CNG·openssl을 하면 딸려온다. 고유의 BouncyCastle.NET 탐지는 소스/패키지 = **위임 레인**(§0.1).
- **Go** — 위 2.1대로 `REBUILD`로 흡수.

즉 §0.5의 "후속 목록"은 **peer 후보 목록이 아니라, 대부분 openssl/CNG로 귀속되는 표면 목록**이다.
진짜 새 substrate/피어를 요구하는 건 **Windows CNG**뿐이다.

### 확정된 로드맵 — CNG 단계적 도입

이 검증의 결론에 따라 CNG는 **한 번에가 아니라 릴리스별로** 도입한다(CNG는 디스커버리 절반은
지금 계약에 얹히나 프로비저닝 절반은 새 substrate를 요구하므로):

| 릴리스 | 범위 | 상태 |
|---|---|---|
| **v0.1.0** | 스키마 예약 — `CRYPTO_RUNTIME_WIN_CNG` + `CngAxes`(provider_set 최소) | ✅ 반영(미구현) |
| **v0.2.0** | 디스커버리 — Windows 콜렉터 → `CngAxes` 채움 → 인벤토리 수렴 | ⬜ 계획 |
| **v0.3.0** | 프로비저닝 — substrate 일반화 선행 → `renderCNG`(레지스트리/GPO) | ⬜ 계획 |

`CngAxes`는 provider 동형성이 보장하는 `provider_set`만 예약했다 — OS 빌드·등록 방식 등 실물 관측이
정할 필드는 v0.2.0에서 **번호를 새로 부여해 추가**한다(proto3 additive). substrate 일반화는 v0.3.0에서
**Windows 구현이 손에 있을 때** 하고, 지금 미리 뽑지 않는다(투기적 추상화 금지).

## 부록 — 이 노트가 확정하지 않은 것 (열린 채로 둔다)

- **HSM axis의 실제 필드**(슬롯·모듈 경로·펌웨어 버전 등)는 실물 PKCS#11 관측 사례가 있을 때 정한다.
- **substrate 추상 인터페이스의 seam**(File-Stage vs Registry/GPO vs Config-Only)은 **Windows 구체
  구현이 손에 들어올 때** 그것을 근거로 뽑는다. 지금 미리 뽑지 않는다.
- **착수 시점**: 위 어느 것도 실사용 수요/투자 결정 전에는 구현하지 않는다. 이 노트는 *"어떤 플랫폼이
  오든 계약이 버티는가"* 를 종이에서 검증했을 뿐, 무엇을 언제 지을지의 신호는 코드 밖(수요)에 있다.
