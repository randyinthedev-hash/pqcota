01

CE 범위 관점 — 이 리포는 어디까지인가

가장 중요한 경계. CE는 관측·정규화·영속·생성까지 — 사실을 수집·파생·생성하되 판단·실행(remediation apply)은 하지 않는다. 3단계 CORE 트랙이 contracts/ SSOT를 이음새로 흐르고, 각 단계마다 실행·거버넌스는 점선(이 리포 밖)으로 갈라진다.

경계의 논리 — 관측성(디스커버리)은 상품화 중이라 방어 불가 → OSS로 풀어 생태계 선점. 반대로 대조·판정·거버넌스·L3 실행은 별도 비공개 리포에 둔다. CE가 관측을 생산하고, 소비자는 이를 contracts/ 계약으로만 소비한다.
02

모듈 아키텍처 관점 — 규정서 3단계의 코드 투영

§2.1 모듈 맵. 각 단계가 append-only 히스토리 계열을 낳고, Provenance/Audit가 네 계열을 봉합한다. Collector는 intake 계약 뒤에 은닉된다. Provisioning은 이제 생성까지만 — 실행·오케스트레이션·L3은 이 리포 밖.

파생 뷰 재현성(§0.2) — 파란 파이프라인이 만드는 것은 전부 raw_capture에서 재계산 가능한 파생 뷰다. 파생 테이블은 derived_from_snapshot_id·ruleset_version을 항상 보유한다.
03

자산·식별 모델 관점 — Machine → Application → Process

식별 안정성이 계층마다 다르다(§4A.2). 머신은 node_id로 안정, 앱은 (node_id, app_key)로 전역 유일, 프로세스는 PID가 휘발이라 저장하지 않고 프로비저닝 직전 실시간 해소한다. 왼쪽은 자산 계층, 오른쪽은 그 계층을 떠받치는 3층 UID 분리.

비밀 미영속(§4A.3) — 접근 비밀(SSH 키·비밀번호·계정)은 어떤 스키마에도 필드가 없다. MachineEndpoint가 대표 — 타입상 비밀을 담을 수 없어 컴파일 타임에 보장된다. 비밀은 hosts 파일→Ansible 전달 후 버린다.
04

Provenance 레인 관점 — 데이터가 어디서 왔는가

모델을 관통하는 첫 원칙(§0.2/§0.3): 데이터를 출처로 레인을 나누고 섞지 않는다. 관측·선언·파생·행위 네 레인. node_id가 전 레인을 꿰는 앵커이고, app_key(s)가 크립토 자산을 앱에 귀속시켜 discovery→provisioning까지 흐른다.

왜 레인을 나누나 — 이 구분이 없으면 Inventory의 3-상태 대조가 성립하지 않는다. 선언 vs 관측은 전달 방식이 아니라 봉투의 detection_method로 갈린다 — 같은 임포트라도 CBOM(관측)과 CMDB(선언)는 다른 레인이다.
05

디스커버리 2-레인 관점 — 만드는 것 vs 위임하는 것

CI가 볼 수 있는 소스/아티팩트(S9)는 CBOMkit에 위임·수신만, 런타임만 볼 수 있는 것(S1·S2·S3)은 자체 구현(해자). network-collector는 노드의 능력이 아니라 실제 posture(그 연결이 정말 PQC로 협상됐나)를 본다 — 이 둘의 대조가 핵심.

능력 vs 실제 오버레이(인벤토리 §12.2) — 노드에 "PQC 가능 lib 로드"(Finding)와 엣지 "실제 고전 협상"(관측)을 겹치면 "PQC 되는데 고전으로 폴백 중" 같은 정확한 다음 액션이 드러난다. 이게 network-collector를 따로 두는 이유다.
06

성숙도 × Posture 관점 — 직교하는 두 축이 remediation을 라우팅

§3.4. posture 축("PQC냐 고전이냐": 🟢🔴⚪)과 성숙도 축("표준이냐 실험이냐")은 직교한다. 관측된 협상 그룹을 MatchPQC()로 정규화·매칭해 성숙도를 파생하고, 그 둘의 조합이 조치(action)와 우선순위를 결정한다. 파생일 뿐 실행은 이 리포 밖.

목표 표준은 종류별로 갈린다 — KEM→ML-KEM(FIPS 203), 서명→ML-DSA(FIPS 204). 이 권고는 파생일 뿐 실행이 아니다 — 실제 remediation 실행·오케스트레이션은 이 리포 밖. CE는 "무엇을 해야 하는가"까지만 정직하게 낸다.
07

폴리글랏 스택 관점 — 대상 런타임이 언어를 강제한다

스택은 취향이 아니라 수집 능력의 기술적 제약이 결정한다(§1.1). 특히 Security.getProviders() 실체 조회는 JVM 안에서만 가능해 폴리글랏이 불가피하다. 배포 바이너리는 정적(CGO_ENABLED=0)이라 OS가 아니라 arch별 교차 컴파일이다.

왜 Go 코어인가 — eBPF 생태계 정렬(cilium/ebpf) · 단일 정적 바이너리 배포 · Ansible/gRPC 관성. 순수·고립 모듈인 ELF 심볼 분석기는 나중에 Rust로 스왑 가능한 후보(intake 계약 뒤에 숨음).
08

라이선스 격리 관점 — 소비 형태가 의무를 가른다

라이선스 의무는 "배포 바이너리에 링크되는가"로 완전히 달라진다. 제품 바이너리에 링크·번들되는 서드파티는 전부 허용적(Apache/MIT/BSD)뿐이고, 카피레프트(GPL)는 오직 별도 프로세스로 실행되는 도구에만 존재하며 프로세스 경계로 전염이 차단된다(§6.2).

격리 3원칙(§6.2) — ① 별도 프로세스 실행(라이브러리 링크 금지) · ② 표준 데이터만 교환(gRPC/CLI + CycloneDX) · ③ 배포 분리(별도 리포, CI 라이선스 스캐너가 교차 의존 게이트). ⚠️ 배포 전 변호사 실사 필수 — 본 문서는 법률 자문 아님.
+

관통 원리 관점 — 자동화 등급과 증거 강도

전 단계를 지배하는 두 척추. AUTO/PROPOSE/MANUAL(§0.1)이 자동화 경계를, detection_method → evidence_strength의 결정론적 함수(§2.4)가 "무엇을 얼마나 믿는가"를 정한다. 채우지 못한 필드는 nil이 아니라 명시적 unknown(enum 0 = *_UNSPECIFIED).
