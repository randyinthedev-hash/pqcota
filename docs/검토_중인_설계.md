# 검토 중인 설계 — 아직 짓지 않은 것

> **코드를 바꾸지 않는 문서다.** 로드맵에 올라왔지만 구현을 확정하지 않은 것들의 설계를 여기서
> 진행한다. 본 설계 문서(디스커버리·인벤토리·프로비저닝)는 **지금 서 있는 것만** 적는다 — 검토 중인
> 것이 섞이면 무엇이 사실이고 무엇이 계획인지 갈리지 않는다.

**수명** — 항목은 넷 중 하나로 끝난다.

| | |
|---|---|
| **① 로드맵 등재** | 방향이 생기면 [로드맵](../RELEASE_NOTES.md#로드맵--예정-릴리스-계획)에 한 줄, 설계는 여기서 |
| **② 여기서 설계** | 코드 무변경. 무엇이 걸리고 무엇을 정해야 하는지까지 |
| **③ 본 설계로 승격** | 구현 계획이 확정되면 해당 단계 설계 문서에 반영하고 **여기서는 지운다** |
| **④ 안 하기로** | 로드맵의 [「안 만드는 것」](../RELEASE_NOTES.md#로드맵에-없는-것--안-만든다)으로 옮긴다 |

여기 남아 있다는 것은 **아직 결정되지 않았다**는 뜻이다. 착수 신호는 코드 밖(실사용 수요)에 있다.

---

## 1. provider 생태계 수용 — 아는 이름이 셋뿐이다

**무엇이 문제인가.** 지금 코드가 이름만으로 확정할 수 있는 provider는 `oqsprovider`(OpenSSL) ·
`BC` · `BCFIPS`(JCA) 셋이다. 그 밖의 이름은 JCA면 `providerClass`(FQCN)를 계획에 함께 적어야 하고,
OpenSSL이면 경로만 맞으면 되지만 **어떤 이름을 쓸 수 있는지 사용자가 알 길이 없다.**

PQC provider 생태계는 이미 그보다 넓다.

| 프로젝트 | 형태 | 지금 상태 |
|---|---|---|
| [oqsprovider](https://github.com/open-quantum-safe/oqs-provider) | OpenSSL provider | ✅ 이름으로 확정 |
| [BouncyCastle](https://www.bouncycastle.org/) 1.80+ · BC-FIPS | JCA | ✅ 이름으로 확정 |
| [wolfProvider](https://github.com/wolfSSL/wolfProvider) | OpenSSL provider (wolfCrypt) | ⬜ 이름 미등록 |
| [pkcs11-provider](https://github.com/openssl-projects/pkcs11-provider) | OpenSSL provider (HSM backend) | ⬜ §2 참조 |
| oqsprovider 파생(벤더 빌드) | OpenSSL provider | ⬜ 이름 미등록 |

**정해야 하는 것** — 이름 목록을 **코드에 더 박을지, 문서로 뺄지**다. 코드에 박으면 새 provider마다
릴리스가 필요하고, 문서로 빼면 사용자가 `providerClass`를 직접 적는 대신 목록을 보고 고른다.
지금 구조상 OpenSSL은 이름이 자유롭고(경로만 맞으면 된다) JCA만 FQCN이 필요하므로, **JCA 이름표를
문서로 두는 쪽**이 유력하다.

## 2. OpenSSL 쪽 FIPS provider — 규제 자산에 답이 없다

**여기가 실제 공백이다.** 규제 자산(`fips_validation` 요구)을 만나면 조치는 FIPS 검증 provider로
라우팅돼야 하는데(§4.10), 지금 그 답이 **JCA에만** 있다 — `BCFIPS`. OpenSSL 자산이 규제 대상이면
taxonomy가 조치를 내지만 **어느 provider를 쓰라고는 말하지 못한다.**

후보는 [wolfProvider](https://github.com/wolfSSL/wolfProvider)다 — OpenSSL 3.x 전 버전에 붙고
`--enable-pqc`로 ML-KEM·ML-DSA를 내며 FIPS 갈래가 있다. 배치 형태가 `.so` + `provider_sect`라
**taxonomy 변경 없이** 들어온다.

**정해야 하는 것** — FIPS 검증본의 식별이다. "이 `.so`가 FIPS 검증된 빌드인가"는 파일만 봐서
알 수 없다. 지금 JCA는 provider **이름**(`BCFIPS`)으로 가르는데 OpenSSL에는 그런 규약이 없다.
사용자가 계획에 명시하게 할지, 관측으로 가를 수 있는지가 열려 있다.

## 3. OpenSSL provider 관측 — 지금은 볼 수 없다

**여기가 가장 큰 공백이다.** 두 런타임의 관측 깊이가 다르다.

| | provider 관측 |
|---|---|
| **JCA** | attach → `getProviders()` → **provider 체인 전부**(순서 포함) |
| **OpenSSL** | **없음** — `/proc/<pid>/maps`로 lib 경로, ELF 문자열로 fork·버전까지다 |

그래서 **`oqsprovider`가 이미 설치돼 있는지조차 모른다.** 조치를 생성할 때 "이미 있는 것을 또
넣는 것인지"를 판단할 근거가 없고, 사용자가 손으로 깔아둔 provider도 인벤토리에 안 잡힌다.

**정해야 하는 것** — 어떻게 볼 것인가다. `openssl.cnf`의 `provider_sect`를 읽는 것은 **설정을
읽는 것이지 실행 중 상태가 아니다**(§2.4 기준으로는 `artifact` 레인, 강도가 한 단계 낮다).
로드된 모듈을 `/proc/<pid>/maps`에서 찾는 방법은 provider가 `.so`로 매핑되므로 가능해 보이지만,
그 `.so`가 provider인지 아닌지를 무엇으로 가를지가 열려 있다.

fork 시그니처(`OpenSSL`·`AWS-LC`·`BoringSSL`·`LibreSSL`)를 늘리는 것은 **이 문제와 층이 다르다** —
fork는 libcrypto 자체가 어느 구현체인가이고, provider는 그 위에 얹히는 모듈이다. 그리고 `fork`
값은 지금 조치 선택에 쓰이지 않는다(`Remediate`는 알고리즘 이름과 규제 여부만 본다) — 인벤토리
표기용이다. 늘릴 값은 있지만 우선순위는 낮다.

## 4. HSM backend target 축

[런타임 확장 계약](런타임_확장_계약.md)이 *"HSM은 새 런타임이 아니라 openssl/jca provider의
**backend target**"* 으로 결론냈다. 배치는 `pkcs11-provider`로 되지만 **슬롯·모듈 경로·펌웨어 같은
backend 정보를 담을 축이 아직 없다.**

**정해야 하는 것** — 그 노트가 열어둔 그대로다. 실물 PKCS#11 관측 사례가 있을 때 필드를 정한다.
