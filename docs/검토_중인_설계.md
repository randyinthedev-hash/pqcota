# 검토 중인 설계 — 아직 짓지 않은 것

> **코드를 바꾸지 않는 문서다.** 로드맵에 올라왔지만 구현을 확정하지 않은 것들의 설계를 여기서
> 진행한다. 본 설계 문서(디스커버리·인벤토리·프로비저닝)는 **지금 서 있는 것만** 적는다 — 검토 중인
> 것이 섞이면 무엇이 사실이고 무엇이 계획인지 갈리지 않는다.

**수명** — 항목은 넷 중 하나로 끝난다.

| | |
|---|---|
| **① 로드맵 등재** | 방향이 생기면 [로드맵](../RELEASE_NOTES.md#로드맵--예정-릴리스-계획)에 한 줄, 설계는 여기서 |
| **② 여기서 설계** | 코드 무변경. 무엇이 걸리고 무엇을 정해야 하는지까지 |
| **③ 본 설계로 승격** | 구현 계획이 확정되면 해당 단계 설계 문서에 반영하고 **여기서는 지운다** |
| **④ 안 하기로** | 로드맵의 [「안 만드는 것」](../RELEASE_NOTES.md#로드맵에-없는-것--안-만든다)으로 옮긴다 |

여기 남아 있다는 것은 **아직 결정되지 않았다**는 뜻이다. 착수 신호는 코드 밖(실사용 수요)에 있다.

---

## 1. provider 수용 — "지원한다"의 뜻

**경계부터.** provider의 선택·조달·FIPS 검증서 확인은 계획을 쓰는 사용자가 한다(`providerChoice`는
계획의 입력이고, 모듈 파일도 사용자가 둔다). 이 리포가 하는 일은 세 층이고, 층마다 비용이 다르다:

| 층 | 하는 일 | 지금 상태 |
|---|---|---|
| **L0 배치 메커니즘** | 스테이징·sha256 게이트·롤백이 그 `.so`를 받는다 | ✅ provider 무관 — 이미 전부 됨 |
| **L1 config 어휘** | 렌더가 **그 provider가 요구하는 조각**을 낸다 | ⚠ 지금은 `activate = 1` + `module = 경로` 한 모양뿐 |
| **L2 실물 확인** | 실물로 종단(배치→활성→관측)을 확인하고 후보 표에 표기 | ◐ oqsprovider만 확인됨 — 나머지 후보는 미확인 |

**"wolfProvider를 지원한다" = L1이 그 provider의 config 모양을 아는 것 + L2 확인.** 후보별로 L1
요구가 다르다는 것이 이 항목의 실체다:

| 후보 | L1에 필요한 것 |
|---|---|
| [oqsprovider](https://github.com/open-quantum-safe/oqs-provider) | 현행 모양으로 충분(activate+module) — **L2 확인됨**(아래) |
| [wolfProvider](https://github.com/wolfSSL/wolfProvider) | 현행 모양으로 충분해 보이나 **실물 미확인** |
| OpenSSL 자체 `fips` 모듈 | **다른 모양** — `fipsinstall`이 만드는 `fipsmodule.cnf` include가 필요. 규제 자산의 표준 답이 되려면 이 조각을 렌더가 알아야 한다 |
| [pkcs11-provider](https://github.com/openssl-projects/pkcs11-provider) | **다른 모양** — PKCS#11 드라이버 경로 등 provider별 키가 더 필요. §3(HSM 축)과 붙어 있다 |
| JCA 커스텀 | 렌더 변경 불요 — `providerClass`(FQCN)가 이미 일반 경로 |

FIPS 검증본 확인은 사용자가 한다(검증서는 빌드 단위라 파일만 봐서 모른다). 도구가 보장하는 것은
**사용자가 고른 그 파일이 그대로 배치됐다**(sha256)까지다.

**L2 확인 기록 — oqsprovider (2026-08-06).** `PROVIDER_INJECT`가 겨냥하는 대역(3.0–3.4)의 실물
OpenSSL 3.0.13에서, **도구가 낸 계획·플레이북·config만으로** 종단을 확인했다.

| | |
|---|---|
| 조치 전 | `openssl list -kem-algorithms \| grep -ci mlkem` → **0** |
| 조치 후 | **14개** · `openssl list -providers`에 `oqsprovider … status: active` |
| 되돌린 뒤 | 다시 **0** — 가역성까지 같은 경로로 확인 |

렌더가 낸 조각의 어휘(`activate = 1` + `module = 경로`)는 이 후보에 충분했다 — L1은 그대로 둔다.

다만 **확인 과정에서 렌더의 결함 하나가 드러났다**: 최상위 `openssl_conf = openssl_init`이 없어,
조각을 `OPENSSL_CONF`로 직접 가리키는 환경에서는 배치도 되고 sha256 게이트도 통과하는데 provider가
올라오지 않았다. 고쳤고(`pkg/provisioning/openssl.go`) 회귀 테스트를 붙였다. **실물로 끝까지 가보지
않았으면 못 찾을 종류의 결함**이라, 이 항목이 L2를 요구하는 이유 자체이기도 하다.

데모에서 `DEMO_REAL_PROVIDER=1`로 이 경로를 재현할 수 있다([데모 README](../demo/README.md#선택-단계--실물-provider로-마지막-한-칸까지-demo_real_provider1)).

**정해야 하는 것** — ① L1을 어떻게 여나: provider별 조각을 코드에 하나씩 넣을지, 계획에 config
조각을 실을 자리(`extraConfig` 류)를 열지. 후자는 렌더 변경 없이 후보 전부를 받지만 "지어내지
않는다" 원칙과 저울질이 필요하다. ② 후보 표를 어디 두나: [plans README](../examples/provisioning/plans/README.md)가 유력하다.

## 2. OpenSSL provider 관측 — 지금은 볼 수 없다

두 런타임의 관측 깊이가 다르다. **버전은 양쪽 다 관측된다**(OpenSSL은 ELF 문자열에서 —
`libcrypto.so.3 3.0.13`처럼 인벤토리에 실린다). 다른 것은 provider 층이다.

| | provider 관측 |
|---|---|
| **JCA** | attach → `getProviders()` → **provider 체인 전부**(순서 포함) |
| **OpenSSL** | **없음** — `/proc/<pid>/maps`로 lib 경로, ELF 문자열로 fork·버전까지다 |

그래서 **`oqsprovider`가 이미 설치돼 있는지는 모른다.** 프로비저닝을 막는 공백은 아니다 —
계획 확정은 사용자의 일이고 버전 근거는 인벤토리에 있다(§2 끝 참조). 이 관측이 주는 것은
**참고 정보**다: 이미 있는 provider의 중복 배치를 피하고, 손으로 깔아둔 것을 인벤토리에 잡는다.

**정해야 하는 것** — 어떻게 볼 것인가다. `openssl.cnf`의 `provider_sect`를 읽는 것은 **설정을
읽는 것이지 실행 중 상태가 아니다**(§2.4 기준으로는 `artifact` 레인, 강도가 한 단계 낮다).
로드된 모듈을 `/proc/<pid>/maps`에서 찾는 방법은 provider가 `.so`로 매핑되므로 가능해 보이지만,
그 `.so`가 provider인지 아닌지를 무엇으로 가를지가 열려 있다.

fork 시그니처(`OpenSSL`·`AWS-LC`·`BoringSSL`·`LibreSSL`)를 늘리는 것은 **이 문제와 층이 다르다** —
fork는 libcrypto 자체가 어느 구현체인가이고, provider는 그 위에 얹히는 모듈이다. 그리고 `fork`
값은 지금 조치 선택에 쓰이지 않는다(`Remediate`는 알고리즘 이름과 규제 여부만 본다) — 인벤토리
표기용이다. 늘릴 값은 있지만 우선순위는 낮다.

## 3. HSM backend target 축

[런타임 확장 계약](런타임_확장_계약.md)이 *"HSM은 새 런타임이 아니라 openssl/jca provider의
**backend target**"* 으로 결론냈다. 배치는 `pkcs11-provider`로 되지만 **슬롯·모듈 경로·펌웨어 같은
backend 정보를 담을 축이 아직 없다.**

**정해야 하는 것** — 그 노트가 열어둔 그대로다. 실물 PKCS#11 관측 사례가 있을 때 필드를 정한다.
